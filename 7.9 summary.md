# 2026-07-09 Quest3-Franka Teleoperation Summary

This document summarizes the work done on July 9 for Quest 3 controller teleoperation and data recording on the Franka FR3 setup.

## 1. Main Goal

The goal today was to make Quest 3 controller teleoperation usable for Franka data collection, with data saved in LeRobot/HuggingFace format for later StarVLA fine-tuning.

The target action alignment remains:

```text
7D delta end pose:
[dx, dy, dz, droll, dpitch, dyaw, gripper]
```

This is the cleaner long-term direction because it matches the original StarVLA/LIBERO style action space better than 8D delta joint control:

```text
Quest 3 controller motion
-> delta end-effector pose
-> /phone_pose and /phone_gripper
-> recorder/env
-> /target_pose
-> cartesian_impedance_controller
```

For current recording, Quest orientation streaming is disabled in the recording adapter:

```text
rotation_scale = 0.0
```

So the recorded action is still 7D, but the rotation delta is normally near zero:

```text
[dx, dy, dz, 0, 0, 0, gripper]
```

```bash
--disable-recorder-gripper-control
```

the recorder should not execute gripper commands itself.

## 3. Quest Tracking and Passthrough

A key practical lesson today:

```text
The headset must be worn / awake / active.
```

If the headset is not worn, Quest tracking may stop, and these topics may appear to have no data:

```text

/quest/right_controller/joy
```

This is not necessarily a bridge failure. The Quest app can be launched successfully but still not output active tracking if the headset is asleep or not worn.

## 4. Controller Launch and Environment Problems

A repeated issue was:

```text
PackageNotFoundError: "package 'franka_description' not found, searching: ['/opt/ros/humble']"
```

Cause:

```text
The Franka controller launch was started without sourcing /home/ros/ros2_ws/install/setup.bash inside the docker container.
```

Correct controller launch environment:


Then launch:

```bash
ros2 launch /home/ros/ros2_ws/src/crisp_controllers_demos/crisp_controllers_robot_demos/launch/franka_cartesian_impedance.launch.py \
  arm_id:=fr3 \
  robot_ip:=172.16.0.2 \
  use_fake_hardware:=false \
  use_rviz:=false
```

Another important lesson:

```text
franka.launch.py is not the correct path for Quest Cartesian body teleop.
```

When the wrong launch was used, the gripper could move but Franka body motion did not work. The correct launch for `/target_pose` body teleop is:

```text
franka_cartesian_impedance.launch.py
```

## 5. Stale Node Problem

Several failures were caused by stale ROS nodes still running in the background.

Examples of stale nodes:

```text
/quest3_stream_adapter
/recording_manager
/robot_client
/gripper_client
/quest_reader_ros_bridge
/servo_reader_node
```

The dangerous stale publishers were:

```text
/target_pose publisher: robot_client or quest3_stream_adapter
/gripper/gripper_position_controller/commands publisher: gripper_client or quest3_stream_adapter
/servo_angles publisher: servo_reader_node
```

Important discovery:

```text
When controller died, old recorder/adapter nodes could remain alive and keep publishing.
If the controller was restarted while old publishers were still alive, Franka could receive stale commands immediately.
```

Clean-up command used today:

```bash
pkill -9 -f quest3_stream_adapter
pkill -9 -f record_lerobot_format_leader_follower
pkill -9 -f quest_reader_ros_bridge
pkill -9 -f crisp_gym.scripts.record_lerobot_format_leader_follower
pkill -9 -f crisp_gym.scripts.quest3_stream_adapter
```

Then refresh ROS daemon:

```bash
source /opt/ros/humble/setup.bash
export ROS_DOMAIN_ID=30

ros2 daemon stop
ros2 daemon start
```

Then check:

```bash
ros2 node list | grep -E "quest3_stream_adapter|recording_manager|robot_client|gripper_client|quest_reader_ros_bridge"
```

Expected output before clean restart:

```text
no output
```

Leader arm residue was also found:

```text
/servo_reader_node
/servo_angles
```

It was not controlling Franka because `/servo_angles` had no subscriber, but it should still be killed before Quest teleop:

```bash
docker exec franka bash -lc 'pkill -9 -f servo_reader.py'
```

## 6. Gripper Problem and Fixes

The main gripper problem:

```text
Trigger was held, Franka gripper closed, then automatically opened.
```

Confirmed expected input:

```text
Trigger held:
/phone_gripper data: 0.0

Trigger released:
/phone_gripper data: 1.0
```

The problem was not only the Quest trigger value. The root causes were:

1. Multiple gripper-related publishers could exist.
2. The recorder/env could still call `env.gripper.open()` during reset/end.
3. The Franka hand adapter acted on one-frame open commands too easily.
4. Stale recorder nodes could keep a `gripper_client` alive after controller restart.

Code changes made:

### 6.1 Franka hand adapter open debounce

File:

```text
src/crisp_controllers_demos/crisp_controllers_robot_demos/crisp_controllers_robot_demos/crisp_py_franka_hand_adapter.py
```

The hand adapter was changed so that:

```text
close command: closes once when commanded closed
open command: must be stable for open_command_hold_sec before opening
```

This avoids opening from a short trigger glitch.

After changing this file, the package must be rebuilt inside docker:

```bash
docker exec -it franka bash
cd /home/ros/ros2_ws
source /opt/ros/humble/setup.bash

colcon build --packages-select crisp_controllers_robot_demos --symlink-install
source install/setup.bash
export ROS_DOMAIN_ID=30
```

### 6.2 Recorder gripper control disabled more completely

File:

```text
src/crisp_gym/crisp_gym/scripts/record_lerobot_format_leader_follower.py
```

The recorder was changed so that when:

```bash
--disable-recorder-gripper-control
```

is used, the recorder does not call gripper open at episode reset/end.

This is important because the Quest adapter is the intended gripper controller during Quest recording.

## 7. Standard Pose Behavior

The standard pose is controlled by this recorder argument:

```bash
--use-current-pose-as-episode-start
```

Meaning:

```text
The exact Franka pose at recorder startup is captured as the episode start pose.
After each save/delete, the robot returns to that captured pose.
```

Important consequence:

```text
If controller dies near the cube and recorder is restarted there,
that wrong cube-side pose becomes the new standard pose.
```

Correct recovery flow after controller death:

```text
1. Stop adapter and recorder.
2. Restart Franka controller.
3. Move Franka back to the intended standard pose.
4. Start recording adapter.
5. Start recorder.
```

Do not restart recorder while the robot is stuck near the cube.

## 8. Standard Pose Adjustment

Two methods were used to adjust standard pose.

### 8.1 Direct Quest adapter

Direct adapter publishes `/target_pose` itself:

```text
Quest controller
-> quest3_stream_adapter with publish_target_pose:=true
-> /target_pose
-> cartesian_impedance_controller
```

This is only for adjusting the standard pose, not for recording.

After the robot reaches the desired standard pose:

```text
Ctrl+C direct adapter
Start recording adapter
Start recorder
```

### 8.2 Joint 7 nudge

Joint 7 was nudged to adjust wrist/gripper angle:

```text
fr3_joint7 += 0.05 rad
```

This succeeded:

```text
Moved fr3_joint7 by +0.05 rad
```

This was done through `/target_joint` under joint impedance controller. After that, Cartesian controller needed to be restarted for Quest teleop.

Important:

```text
Changing joint 7 changes the nullspace/wrist posture.
Quest Cartesian motion may feel different afterward.
```

If motion feels strange, possible causes are:

1. Wrist posture changed.
2. Adapter was not restarted/re-anchored.
3. Old `/target_pose` publishers remain.

## 9. Controller Dies Near Cube

Observed behavior:

```text
When Franka was just about to reach the cube, controller could die.
Franka then stayed near the cube.
```

Likely causes:

```text
too close to cube/table
force/torque threshold reached
Cartesian impedance fighting contact
target pose keeps going down while robot is physically blocked
motion step too aggressive near contact
```

Recommended response:

```text
Stop teleop immediately.
Do not restart recorder at the stuck pose.
Clean old nodes.
Recover/restart controller.
Move back to standard pose.
Use smaller max_translation_step near contact.
```

## 10. Downward Motion and Shake

Two symptoms appeared near the cube:

```text
Franka could not go very down.
There was slight shake while trying to pick up the cube.
```

Interpretation:

```text
This is probably not only z_scale.
It may be safety/contact/controller behavior.
```

If `/target_pose.z` keeps decreasing but Franka does not move down, then the Quest mapping is working and the limit is on the robot/controller/contact side.

Check:

```bash
source /opt/ros/humble/setup.bash
export ROS_DOMAIN_ID=30

ros2 topic echo /target_pose --field pose.position
```

If `z` changes but the robot does not go down:

```text
robot/controller/safety/contact limit
```

If `z` does not change:

```text
adapter/recorder/deadman input issue
```

## 11. Current Parameter Direction

Earlier more aggressive recording parameters:

```text
translation_scale = 0.7
x_scale = 1.2
y_scale = 1.2
z_scale = 1.5
max_translation_step = 0.010
```

These moved faster but could be risky near the cube.

More stable parameters suggested after shake:

```text
translation_scale = 0.45
x_scale = 1.1
y_scale = 1.1
z_scale = 1.2 to 1.4
max_translation_step = 0.006
```

Then user asked to increase z-scale. Safer current choice:

```text
z_scale = 1.4
max_translation_step = 0.006
```

If still too weak:

```text
z_scale = 1.6
max_translation_step still 0.006
```

Do not increase both z_scale and max_translation_step aggressively near cube contact.

## 16. Final Lessons From Today

1. Wear the Quest headset when checking Quest tracking topics.
2. Use `franka_cartesian_impedance.launch.py` for Quest body teleop.
3. Do not restart recorder when Franka is stuck near the cube; it would capture the wrong standard pose.
4. Clean stale ROS nodes before restarting controller.
5. Gripper should be controlled by Quest adapter; recorder should record gripper but not execute it.
6. Near cube contact, reducing step size is often safer than increasing scale.
7. Increasing z-scale can help, but only together with conservative `max_translation_step`.
8. Standard pose should be set just above the object, not on contact with the object/table.
9. Joint nudges can help standard pose, but they change Cartesian motion feel.
10. For recording, the safest final flow is:

```text
clean old nodes
start Franka cartesian controller
start Quest app
start Quest bridge
start recording adapter
verify /phone_pose and /phone_gripper
start recorder
record episodes
```
